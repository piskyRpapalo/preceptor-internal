### 1.2 UMT no es "Universal Machine Token". Es "Universal Machine **Time**".

El plano trataba UMT como si fuera un token/credencial que acompaña a la atestación.
No lo es. UMT es la **primera implementación on-chain del Precision Time Protocol (PTP)**:
sirve para que máquinas y robots sincronicen su reloj con precisión de nanosegundos contra
un reloj maestro derivado de la cadena.

- Doc oficial: <https://docs.peaq.xyz/peaqchain/sdk-reference/javascript/umt.md> — *"Universal
  Machine Time (UMT) is the first onchain implementation of the Precision Time Protocol (PTP)"*.
- Anuncio de peaq: <https://www.peaq.xyz/blog/universal-machine-time-umt>
- Repo: <https://github.com/peaqnetwork/Universal-Machine-Time-UMT>
- La API es `Sdk.subscribeToPtp({ masterUrl })` → `{ offset, synchronizedTime }`. Es una
  suscripción de **lectura**; no emite credencial alguna.

**Consecuencia para nosotros — y es una buena noticia, no un revés:** UMT sí tiene un papel
en el Faro, pero otro. El payload del Faro lleva `"t": <unix segundos>` puesto por
`int(time.time())` en la-fragua. Un comprador de atestación de recepción puede preguntar,
con razón, *quién garantiza ese reloj*. UMT es exactamente la respuesta estándar del
ecosistema. **Deja de ser un ingrediente de la atestación y pasa a ser una mejora de calidad
del timestamp — candidata a Paso 3, no a Paso 2.**

### 1.3 peaq Verify: el nombre existe desde 2024; la infraestructura, no

- El framework se anunció el **2024-01-30**: <https://www.peaq.xyz/blog/peaq-launches-depin-data-verification-framework>.
  Ahí ya se decía que **sólo el Tier 1 estaba disponible** ("devices sign data using their own
  private key and store it on the peaq blockchain") y que Tier 2 (patrones/ML) y Tier 3
  (oráculo) llegarían después.
- Dos años y medio después, la doc de peaqOS sigue marcando la capa Verify como
  **"coming soon"**, con el aviso de que *"details on this page are preliminary and may change"*,
  y reconoce que sólo hay eventos **auto-atestados**: una máquina puede declarar trust level 2
  (`Hardware-signed`) pero *"there's no third-party attestation infrastructure behind it yet"*.
  <https://docs.peaq.xyz/peaqos/functions/verify.md>
- Los tres tiers, tal como se documentan hoy:
  <https://docs.peaq.xyz/peaqchain/sdk-reference/javascript/verify/verify.md>
  - **Tier 1** — dato firmado en origen por la propia máquina con su clave privada.
  - **Tier 2** — validación por comparación de patrones contra otros dispositivos de la red.
  - **Tier 3** — confirmación por oráculo externo.
- **NO_DATA**: no he encontrado contrato, precompile ni endpoint concreto que implemente
  Tier 2 o Tier 3 hoy. No hay pallet `Verify` en el runtime de agung (§1.5).
- **NO_DATA**: no existe equivalente de `verify` en el SDK de Python. Las páginas de Verify
  cuelgan sólo del SDK de JavaScript.

**Consecuencia:** en Tier 1, **el Faro ya cumple hoy**. Firma Ed25519 en origen sobre
`dominio + JCS(payload)`. No hay que construir nada nuevo para alcanzar el único tier que
peaq tiene realmente en producción. Y el foso que declara la doctrina — *la capa de confianza
por encima del dato crudo* — sigue vacante en peaq: **Tier 2 y Tier 3 son precisamente lo que
peaq no ha construido**. Eso es una oportunidad, no un obstáculo.

### 1.7 Formato del DID de peaq — decodificado desde bytes reales de agung

Esquema protobuf oficial (`did_document_format.proto`, extraído de
<https://github.com/peaqnetwork/peaq-sdk-py/blob/dev/packages/sdk/peaq_sdk/utils/peaq_proto.py>):

```proto
message VerificationMethod { string id=1; string type=2; string controller=3;
                             string public_key_multibase=4; }
message Signature          { string type=1; string issuer=2; string hash=3; }
message Services           { string id=1; string type=2;
                             optional string service_endpoint=3; optional string data=4; }
message Document { string id=1; string controller=2;
                   repeated VerificationMethod verification_methods=3;
                   Signature signature=4; repeated Services services=5;
                   repeated string authentications=6; }
```

**El dato que decide todo el mapeo** (de
<https://github.com/peaqnetwork/peaq-sdk-py/blob/dev/packages/sdk/peaq_sdk/types/did.py>):

```python
class VerificationMethodType(str, Enum):
    ECDSA   = "EcdsaSecp256k1RecoveryMethod2020"
    ED25519 = "Ed25519VerificationKey2020"
    SR25519 = "Sr25519VerificationKey2020"
```

**peaq admite `Ed25519VerificationKey2020` de forma nativa.** El Faro firma con Ed25519 desde
el día uno. **No hay que generar ninguna clave nueva para que El Vigía tenga identidad en
peaq.** El método de verificación declara la clave que ya existe. Esto no es una comodidad:
es la diferencia entre un Paso 2 que sólo necesita una firma del carbono y un Paso 2 que
habría exigido tocar material criptográfico nuevo — cosa que la doctrina prohíbe en este nodo.

DID method registrado oficialmente: <https://github.com/peaqnetwork/peaq-did-specifications>
(`"name": "peaq"`, `"status": "registered"`, `"verifiableDataRegistry": "peaq Blockchain"`).
Formato: `did:peaq:<dirección>`, admitiendo tanto EVM (`0x…`) como Substrate (`5…`).

### 1.8 Desviación encontrada en cadena que el SDK oficial no maneja

Leyendo entradas reales de `AttributeStore` aparecen **dos envoltorios distintos** para el
mismo campo `value`:

- **`hex-ascii`** — bytes ASCII que son a su vez el hex del protobuf. Es lo que asume el SDK
  de Python (`did.py::_read` hace `bytes.fromhex(value).decode('utf-8')` y luego
  `bytes.fromhex(...)` otra vez). Ejemplo real: `demo-warehousebot-002`.
- **`raw-proto`** — el protobuf directamente, sin envoltorio hex. Ejemplo real: el DID
  `peaq:did:0x68616e62616f7175616e7361743740676d61696c2e636f6d`, cuyo documento resuelve a
  `did:peaq:5G6gWBgUVavKwkUhckyiC9HoqVrQQSMknyYrJVRAFVjDmegw`.

**El SDK oficial revienta con los segundos.** Nuestro `did_codec.unwrap_did_value()` prueba
los dos y reporta cuál encontró. Es una cicatriz ajena que heredamos gratis por no usar el SDK.

### 1.9 Límites duros del pallet de storage — medidos, no supuestos

`peaq storage supports a simple structure: 64-byte key : 256-byte value`
(<https://docs.peaq.xyz/build/first-depin/store-machine-data>).

**256 bytes es un límite que muerde.** Una firma Ed25519 en base64url ya son 86 caracteres;
una raíz Merkle en hex, 64; un hash de tx NEAR, 44. Sumado con el JSON de envoltura, la
atestación ingenua no cabe. Esto obligó a una decisión de diseño real en §4, con un test que
mide los bytes en vez de confiar.

### 2.1 El payload REAL (leído del código, no inventado)

De `hexelion/faro/main.py::_attest_v1`, y confirmado contra
`hexelion/faro/proofs/epoch_23.json` (lote ya anclado en NEAR testnet, tx
`LD4MQTo41V9eXf5uTMDXUofujzpUMhEoqr3gF3bmF6d`):

```json
{
  "data": {"cog_e2": 20500, "lat_e7": 386511000, "lon_e7": -90782000,
           "mmsi": 263701460, "sog_e2": 0, "heading": 107},
  "kid":  "hxl-attest-1",
  "kind": "ais.position",
  "node": "hexelion.near",
  "prev": "0f83ecd8af3c141df163db092a877d84f7db7fb27fbb7f1e937293caef151975",
  "seq":  23,
  "t":    1780465516,
  "v":    1
}
```

Propiedades que hay que preservar en cualquier mapeo:

- **Cero floats.** Coordenadas en enteros escalados (`lat_e7`, `sog_e2`, `cog_e2`). Un float en
  el payload firmado rompería la canonicalización entre plataformas.
- **Canonicalización JCS / RFC-8785**: `sort_keys=True`, `separators=(",",":")`, UTF-8.
- **Preimagen de firma con dominio separado**: la firma Ed25519 **no cubre el JSON a secas**,
  cubre `b"hexelion-faro-attestation-v1\n" + JCS(payload)`. Quien verifique fuera del Faro
  **debe saberlo**, o toda firma le parecerá inválida. Por eso el DID lo declara
  explícitamente como servicio (§2.3).
- **Cadena de hashes**: `prev` = SHA-256 del canónico del payload anterior. Da orden y
  detecta huecos.
- **Hoja Merkle**: `sha256(0x00 || JCS(payload))`, prefijo RFC-6962 anti-second-preimage.
  Las hojas se agrupan por epoch y la raíz se ancla en NEAR testnet.

### 2.2 Arquitectura de la señal — y una precisión honesta sobre "primera mano"

```
El Vigía (RPi + SDR)  ──AIS crudo──►  la-fragua (funnel :10111)
                                            │
                                            ▼
                                   El Faro (:8100, DRY_RUN)
                                   node = "hexelion-beato-01"
                                   firma Ed25519 kid=hxl-attest-1
                                            │
                       ┌────────────────────┼────────────────────┐
                       ▼                    ▼                    ▼
              /v1/attested          Merkle por epoch      proofs/epoch_NN.json
              (payload+sig)         raíz → NEAR testnet   (bundle verificable)
```

**Precisión que el plano de junio no hacía y hay que hacer:** el receptor físico es
**El Vigía**; quien **firma** es **El Faro en la-fragua** (`node: "hexelion-beato-01"`).
Son dos máquinas distintas. Una atestación de recepción honesta no puede fingir que la firma
nace en la antena.

Dos opciones para el DID, y la recomendación:

- **(A) Un DID por firmante** — `did:peaq:<addr>` = El Faro. Refleja exactamente lo que hay
  hoy. El DID atestigua *"el firmante recibió esta trama del receptor X"*.
- **(B) Dos DIDs encadenados** — uno para El Vigía (receptor) y otro para El Faro (firmante),
  con el segundo como `controller` del primero. Es lo correcto a largo plazo, pero exige que
  El Vigía tenga su propia clave, y **eso es material criptográfico nuevo: decisión del
  carbono, no de esta sesión.**

**Recomendación: (A) para el Paso 2, (B) como objetivo declarado.** Y que el DID diga la
verdad: campo `services` con el rol de cada máquina, sin inflar. Es un DID de *firmante de
recepción*, no de *sensor*.

Ese último servicio no es decorativo: **es lo que permite que un tercero verifique nuestras

Escritura (Paso 2): `peaq_did::add_attribute(did_account, name, value, valid_for)`, o el
precompile EVM `0x…0800` con `addAttribute(address,bytes,bytes,uint32)`.

### 2.4 Mapeo (b): recepción AIS → atestación verificable

Con Verify Tier 2/3 inexistentes (§1.3), la atestación se ancla en `PeaqStorage::ItemStore`,
con el DID aportando la identidad y el material de verificación. Encaje con el modelo peaq:
**Tier 1 — dato firmado en origen por la máquina con su clave privada.** El Faro ya lo cumple.

**El límite de 256 bytes fuerza una decisión.** El artefacto no puede llevar payload completo
+ firma + prueba Merkle. Diseño adoptado — *ancla el vínculo criptográfico, no el dato*:

```json
{"l":"<hoja Merkle, 64 hex>","r":"<raíz del epoch, 64 hex>",
 "s":23,"t":1780465516,"v":1,"x":"<tx del ancla NEAR, 44>"}
```

**224 bytes medidos** para la recepción real seq=23 — cabe, con 32 bytes de margen. La firma
Ed25519 completa y el payload íntegro se sirven por el servicio declarado en el DID.

Esto no es un atajo: un verificador que lea el ítem de peaq obtiene la hoja, la raíz y la tx
del ancla NEAR, y con eso puede (1) pedir el payload al Faro, (2) recomputar la hoja,
(3) verificar la inclusión Merkle contra la raíz, (4) verificar que esa raíz está anclada en
NEAR, y (5) verificar la firma Ed25519 contra la pubkey del DID de peaq. **La confianza en el
Faro no es necesaria en ningún punto de esa cadena.** Eso es el foso.

### 2.5 DÓNDE FIRMA EL CARBONO — explícito, como pide el prompt

**Tres frenos, no uno:**

1. **Ninguna clave de peaq vive en `soberano`.** Ni existe todavía.
2. **`faro_peaq` no puede enviar aunque quisiera.** `KeylessRpc` tiene allowlist cerrada;
   cualquier método de escritura levanta `WriteAttemptError` **antes de abrir el socket**.
   14 tests parametrizados lo verifican (§4.3).
3. **El tipo lo impide.** `PreparedAttestation.submitted` es `Literal[False]`. Pydantic
   rechaza construir un objeto marcado como enviado. Hay un test para eso.
